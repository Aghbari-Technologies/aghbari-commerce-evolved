1. الهوية والقرارات الحاكمة
===========================
اسم المنتج الوحيد في كل موضع مرئي ووثيقة وملف وتقرير هو: «متجر الأغبري» والاسم الإنجليزي «Aghbari Commerce». يمنع إظهار العامري أو Alamri أو Amiri أو «بوابة العامري» كهوية للمنتج. يجوز أن تظهر أسماء العملاء/الموردين الحقيقية في بياناتهم التجارية فقط، لا كاسم المنتج.

1.1 القرارات التي تحسم تعارضات النصوص القديمة
---------------------------------------------

الموضوع | القرار التنفيذي الملزم
------- | ----------------------
هوية المنتج | متجر الأغبري | Aghbari Commerce فقط؛ تحديث العناوين والـ metadata وPWA وPDF/Excel ورسائل الإشعارات حيث يلزم.
أونكس برو | جزء مدمج من التطبيق والمنظومة الموحدة، وليس شاشة/قاعدة تحليل معزولة عن بيانات المتجر. يجوز فصل الطبقات والجداول داخلياً للصيانة، لكن يجب أن تتكامل البيانات والتقارير والحركة والصلاحيات.
البيانات الحية | قاعدة البيانات التشغيلية هي المرجع للطلبات التي ينشئها المتجر وللمخزون الذي يديره. سجلات أونكس المحاسبية/التاريخية تُدمج عبر نموذج موحد مع حفظ مصدرها ومفتاحها وحالة مطابقتها دون ازدواج.
أسعار العميل | يعرض المتجر سعر فئة العميل المعتمدة على بطاقات المنتجات فقط. افتراضياً تُخفى الأسعار والإجماليات من مراجعة الطلب وسجل الطلبات/نسخة الفاتورة الظاهرة للعميل وفق المطلب الأحدث؛ يستطيع المدير تغيير ذلك من إعدادات مستقلة لكل موضع. الإدارة والمحاسب المخوّل يريان القيم الكاملة.
العمل بدون إنترنت | يسمح بقراءة البيانات المخزنة مؤقتاً وعرض آخر تحديث. لا يُعتمد طلب أو حركة مالية أو حجز مخزون دون اتصال؛ تُنفذ على الخادم مع منع التكرار.
الذكاء الاصطناعي المجاني | دعم جميع المزودين المجانيين القابلين للتكامل وقت التنفيذ من خلال محولات مستقلة، مع نماذج مفتوحة المصدر محلية عند توافر خادم مناسب. لا يُفترض بقاء أي خطة مجانية أو سعتها إلى الأبد؛ يجب فحصها دورياً وإتاحة بديل.
WhatsApp | الإرسال الآلي من الخادم لا يتم إلا عبر WhatsApp Business API/مزود رسمي مفعّل ومصرّح به. فتح تطبيق WhatsApp أو رابط wa.me ليس إرسالاً آلياً؛ عند غياب القناة الرسمية تُعرض حالة صريحة ولا يُدّعى الإرسال.
كلمات المرور | لا يُنفذ شرط منع استخدام كلمة مرور نفسها من قِبل عميل آخر؛ لا تُخزن كلمات المرور نصاً ولا يمكن ضمان هذا الشرط بأمان مع hashing سليم. يُطبق فحص القوة، والتجزئة الآمنة، ومعدل المحاولات، ومصادقة إضافية للإدارة.
حساب المالك | يُنشأ عبر Bootstrap آمن لمرة واحدة أو دعوة إدارية موثقة، دون تضمين كلمة مرور ثابتة في الكود أو المستودع أو الوثيقة. تفرض إعادة ضبط كلمة المرور عند أول دخول إن استُخدمت كلمة مؤقتة.

2. التكليف التنفيذي وطريقة العمل على الكود الحالي
=================================================

التوجيه الإلزامي — INSPECT → UNDERSTAND → PRESERVE → COMPLETE → CONNECT → IMPROVE → TEST → FIX → POLISH → VERIFY. يمنع حذف المشروع وإعادة بنائه من الصفر أو استبدال تقنية عاملة لمجرد التفضيل الشخصي.

2.1 قبل أي تعديل
----------------
• فحص المستودع والفرع وGit status وآخر SHA، وسجلات البناء والاختبارات، ثم توثيق baseline قابل للمقارنة.
• فحص package.json والراوتر والواجهات والمكونات والخدمات والـ hooks وواجهات RPC وEdge Functions وسياسات RLS وعمليات migration والـ Storage والتكاملات الحالية.
• مطابقة الشاشات مع قاعدة البيانات والتأكد من أن كل زر واتجاه تنقل يستدعي عملية حقيقية وليست بيانات ثابتة أو Mock أو Stub.
• إنشاء سجل فجوات موحد لكل بند: مكتمل موثق، جزئي، موجود لكنه ضعيف، موجود غير موصول، مفقود وله عقد خلفي، أو مفقود بلا عقد خلفي.
• إعادة استخدام المكونات والجداول والخدمات ومحركات التسعير والاستيراد والصلاحيات القائمة. قبل إنشاء أي محرك جديد، ابحث في السجل المعماري المركزي؛ يمنع تكرار المحركات.
• تنفيذ تغييرات قاعدة البيانات بمهاجرات متوافقة وقابلة للتراجع قدر الإمكان، مع خطة بيانات قبل التعديل وإثبات سلامة البيانات بعده.
• في حال كانت بيئة المشروع الحالية مختلفة عن المتوقع، احفظ التقنية الناجحة الحالية ووثق القرار بدلاً من فرض Flutter/Laravel/Supabase أو غيرها دون مبرر موثق.

2.2 قواعد منع الهدر والإنجاز الشكلي
-----------------------------------
• لا تكرر استكشاف المشروع أو إعادة قراءة كامل المستودع في كل جلسة؛ احفظ Architecture Map وRequirement Registry وملف handoff يذكر آخر SHA وما تم اختباره وما بقي.
• أنجز كل وحدة مترابطة في دورة واحدة قدر الإمكان (واجهة + منطق + قاعدة بيانات + صلاحيات + حالات + اختبار)، ولا تقسم العمل إلى تعديلات بصرية معزولة عن التشغيل.
• لا تعلن PASS بوجود route أو صفحة أو جدول فقط. يلزم نجاح مسار المستخدم الحقيقي وفشل الحالات غير المسموحة وتوافر سجل/لقطة اختبار.
• لا تستخدم بيانات وهمية في الإنتاج. بيانات العرض التجريبية يجب أن تكون موسومة صراحة DEMO وألا تدخل الحسابات والتقارير الحقيقية.
• عند تعذر تكامل بسبب API أو مفتاح أو اشتراك أو صلاحية خارجية، صرّح بالحاجز وحدد ما تم وما يحتاجه المالك، ولا تنشئ نجاحاً وهمياً.

3. معمارية المنصة ومصدر الحقيقة الموحد
======================================
المطلوب تطبيق تجاري واحد بواجهة عميل ولوحة تحكم وبيانات تشغيلية ومحاسبية وذكاء أعمال مشتركة. تُفصل المسؤوليات برمجياً ولا تُعزل النتائج التشغيلية أو التحليلية عن بعضها. تُحدد ملكية كل نوع بيانات صراحة لمنع الكتابة المتعارضة.

3.1 الطبقات المنطقية
--------------------

الطبقة | المسؤوليات
------ | ----------
واجهة المستخدم | Storefront وAdmin وAI Workspaces؛ مكونات RTL قابلة لإعادة الاستخدام، التحقق الأولي، وحالات العرض.
Application / Use Cases | إنشاء الطلب، الموافقة، التسعير، الاستيراد، المطابقة، التصدير، توليد التقرير، إدارة الصلاحيات.
Domain Services | قواعد التسعير، حدود الائتمان، المخزون المتاح، دورة الطلب، احتساب المؤشرات، مطابقة أونكس، قواعد التنبيه.
Data Access | خدمات/مستودعات typed للوصول إلى قاعدة البيانات وRPC وStorage؛ لا توضع قواعد العمل الحساسة داخل الصفحة.
Persistence | قاعدة البيانات الحالية ومهاجراتها والقيود والفهارس والمعاملات وRLS وسجلات التدقيق.
Integrations | Onyx Pro وWhatsApp ومزودو الذكاء وخدمات البريد/الإشعارات وأي Webhooks.
Operations | سجل الأحداث الموحد، الطوابير، مراقبة الأخطاء، النسخ الاحتياطي، المهام المجدولة، استعادة النظام.

3.2 مصدر الحقيقة وملكية السجلات
-------------------------------
• سجل الطلب المنشأ من متجر الأغبري ولقطة سعره وحالته هي الحقيقة التشغيلية لذلك الطلب داخل المتجر، ولا يُعاد حساب الطلب التاريخي بأسعار اليوم.
• سجلات الدفاتر والفواتير والأرصدة التاريخية التي مصدرها أونكس تبقى مرتبطة بمصدر أونكس ورقم السجل/المستند الأصلي وتدخل في لوحات العميل والمالية والتقارير بحسب الصلاحية.
• كل كيان قابل للمطابقة يجب أن يحمل مصدره الخارجي ومعرّفه الخارجي ووقت المزامنة ونسخة التحويل وبصمة الدفعة وحالة المطابقة، مع الاحتفاظ بمفتاح التطبيق الداخلي.
• تعتمد المطابقة على أكواد الأعمال لا معرف قاعدة البيانات وحده: item_code/SKU للصنف، customer_code للعميل، supplier_code للمورد، مع حفظ الأصفار البادئة كنص.
• لا يُمحى أو يصفر سجل من البيانات الحية لمجرد غيابه عن ملف وارد إلا إذا كان ملفاً كاملاً (Full Dataset) وقاعدة الحذف محددة وموافقاً عليها صراحة.
• تُعرض بيانات أونكس ضمن شاشات التطبيق ولوحاته، ويستطيع المدير رؤية الرصيد/المبيعات/الذمم ذات المصدر المحاسبي والبيانات التشغيلية في سياق موحد مع شارة مصدر ووقت آخر مزامنة.

3.3 توحيد الأحداث
-----------------
كل عملية ذات أثر تجاري مهمة تنتج حدثاً مسجلاً مثل ProductUpdated أو PriceChanged أو OrderCreated أو OrderApproved أو StockAdjusted أو OnyxImported أو ReconciliationCompleted. يسجل الحدث في المعاملة نفسها عبر Transactional Outbox ثم تعالجه المستهلكات مع Idempotency، لتغذية التقارير والتنبيهات والكاش والبحث والذكاء الاصطناعي دون تكرار.

4. متجر العميل وتجربة الاستخدام
===============================

4.1 الهوية والواجهة الرئيسية
----------------------------
• اسم المتجر وشعاره في رأس واضح، أيقونة الإشعارات، زر تحديث البيانات، حالة اتصال مفهومة، وسلة ظاهرة بعد تسجيل الدخول.
• عرض يومي في أعلى الصفحة كشريط إخباري/متحرك أو Banner Slider جذاب، يديره المدير من لوحة التحكم مع مدة البداية والنهاية والأولوية والجمهور المستهدف والرابط واللون؛ يوقف الحركة احتراماً لتفضيل تقليل الحركة.
• بحث ذكي سريع أثناء الكتابة بالاسم والكود وSKU والباركود والوصف والعلامة التجارية مع اقتراحات وفلاتر مجموعة/علامة/حالة وتصفية قابلة للمشاركة.
• بطاقات منتجات متساوية ومنظمة تعرض صورة مضغوطة واسم الصنف كاملاً وكوده ووحدته وسعر الفئة المعتمدة فقط وحالة التوفر وحقل كمية مباشر مع زيادة ونقصان وكتابة يدوية وزر إضافة للسلة.
• لا يلزم فتح صفحة تفاصيل المنتج لتحديد الكمية؛ تظل صفحة مستقلة للتفاصيل والصورة المكبرة والوصف والمنتجات المشابهة عند النقر على بطاقة المنتج.
• إظهار الفئات والمنتجات المميزة والأحدث والأكثر طلباً والعروض، مع عرض شبكي/تمرير أفقي حسب الشاشة، وعدم تحميل جميع الصور والبيانات دفعة واحدة.
• دعم قائمة الطلبات وإعادة الطلب وتعديل طلب سابق وفق حالة الطلب وصلاحيات الإدارة، والمفضلة والقوالب الشرائية والمقارنة حيث تتفق مع التطبيق الحالي.
• إخفاء روابط التسجيل الخاصة بالفئات من الواجهة العامة. يظهر خيار «تسجيل الدخول» و«إنشاء حساب جديد» فقط، وتظل روابط الدعوة الثلاثة متاحة للإدارة لإرسالها مباشرة للعملاء.
• إخفاء فئة العميل عن جميع شاشات العميل والفواتير والطلبات والملفات المرسلة. تستخدم الفئة داخلياً لمحرك التسعير والصلاحيات فقط.

4.2 الهوية البصرية والإتاحة
---------------------------
• لوحة ألوان معتمدة: أخضر داكن أساسي، أخضر متوسط للتفاعل، ذهبي للعروض والشارات المهمة، عاجي/أبيض دافئ للخلفيات. يمنع الأصفر القوي المزعج في حقل الكمية النشط؛ يستخدم لون هادئ مع تباين مناسب.
• إدارة الألوان والشعار والصور وأحجام الخطوط ورسائل الترحيب من لوحة التحكم بآلية Design Tokens موحدة، دون إدخال CSS منفصل يخالف النظام العام.
• Arabic RTL افتراضياً في جميع الشاشات والأخطاء والإشعارات والتقارير، مع تجهيز i18n لإضافة الإنجليزية لاحقاً دون إعادة كتابة المكونات.
• تصميم متجاوب بالكامل للجوال واللوحي والكمبيوتر، مع أهداف لمس ملائمة، تنقل لوحة مفاتيح، focus states، تباين WCAG AA حيث ينطبق، وتسميات لقارئات الشاشة.
• دعم Chrome وEdge وFirefox وSafari الحديثة على Windows وAndroid وiPhone/iPad، مع سلوك بديل واضح للميزات غير المدعومة على متصفح معين.

4.3 الكمية والسلة
-----------------
• خانة الكمية تبدأ فارغة/بقيمة مناسبة للمخزون حسب إعداد المدير، وتقبل الكتابة أو الأزرار +/-، وتتحقق من الأعداد العشرية/الوحدات بحسب الصنف والحد الأدنى للطلب.
• إضافة الصنف نفسه مرة أخرى تزيد/تحدث كمية السطر نفسه، ولا تنشئ سطوراً مكررة بلا داعٍ. تعرض شارة السلة عدد الأصناف الفريدة، مع إمكانية إظهار عدد الوحدات الإجمالي كمعلومة منفصلة.
• تمنع الكميات الصفرية والسالبة وتراعي وحدات الكرتون/الحبة/العبوة/الصندوق وMOQ ومضاعفات الطلب إن وجدت.
• الطلب الذي يُرسل لا يختفي بصمت عند الفشل؛ يبقى قابلاً لإعادة المحاولة مع مرجع idempotency يمنع إنشاء طلب ثانٍ لنفس الإرسال.

5. المنتجات والتصنيفات والمخزون

5.1 بطاقة المنتج وبياناته
-------------------------
لكل صنف يجب أن تتوافر الحقول التالية أو ما يعادلها في المخطط الحالي، مع فحص الحاجة لإضافة الحقول الناقصة فقط: صورة/صور، الاسم، item_code، SKU، Barcode، الوحدة الأساسية والوحدات البديلة ومعامل التحويل، التصنيف الرئيسي والفرعي، العلامة التجارية عند وجودها، الوصف، الحالة، الأسعار الثلاثة، الكمية الحالية، الكمية المحجوزة، الكمية المتاحة، الحد الأدنى، تاريخ التحديث، وحقول الدفعة/الصلاحية حيث تنطبق.

5.2 المخزون
-----------
• حساب Available-to-Promise: الرصيد الفعلي ناقص المحجوز والمخصص، مع إضافة الوارد المتوقع الموثوق حسب حالة أمر الشراء/الاستلام.
• حركات مخزون غير قابلة للمحو الصامت: إضافة، صرف، تسوية، حجز، فك حجز، مرتجع، تحويل فرع، استلام توريد. يسجل لكل حركة المستخدم والسبب والكمية السابقة واللاحقة والمرجع والتاريخ.
• حد أدنى لكل صنف قابل للضبط، وتنبيه أصفر/أحمر عند الاقتراب من النفاد أو النفاد، مع قواعد قابلة للتخصيص بحسب الصنف/المجموعة/المخزن.
• لا يجوز أن تتجاوز عمليات متزامنة الرصيد بسبب سباق الطلبات؛ الحجز وتأكيده يتم بمعاملة/قفل ملائم مع اختبار concurrency.
• دعم متعدد المخازن والفروع في النموذج حتى لو بدأ الإطلاق بمخزن واحد، دون فرض واجهة معقدة على المستخدم إذا كانت غير لازمة حالياً.
• معلومات الدفعة وتاريخ انتهاء الصلاحية حيث تتوفر من أونكس أو الإدخال؛ تقارير أقرب انتهاء والأصناف الراكدة والمخزون الراكد ورأس المال المجمد عند وجود تكلفة موثوقة.

6. التسعير الذكي وقواعد الأسعار
===============================

6.1 أسعار الفئات الثلاث
-----------------------
كل منتج له ثلاثة أسعار مستقلة في قاعدة البيانات ومحرك التسعير: جملة الجملة، الجملة، التجزئة. الفئة مستمدة من بيانات العميل الموثقة على الخادم ولا تُقبل من طلب الواجهة. يرسل الخادم للعميل سعر فئته فقط، وتمنع RLS/Views/RPC/API تسرب أسعار الفئات الأخرى حتى عبر أدوات المطور أو تعديل الاستعلامات.

6.2 جدول الأسعار الشامل
-----------------------
• تبويب واحد بصفوف للأصناف وأعمدة للأسعار الثلاثة والسعر الأساسي والوحدة والمخزون والحالة، مع Inline Editing، تنقل Enter للخلية/السطر التالي، حفظ مجمع ومعاينة التغييرات قبل اعتمادها.
• استيراد وتصدير Excel/CSV بقالب ثابت مع المحافظة على الأكواد والأصفار البادئة وصيغة العملة والدقة العشرية. يسجل كل تغيير مع القيمة السابقة والجديدة والمنفذ والسبب.
• تدعم القاعدة: نسبة إضافة على الأساس، هامش ربح من سعر البيع، سعر ثابت، إضافة/خصم مبلغ؛ وتُطبق على مستوى التسعير المحدد لكل فئة (جملة الجملة/الجملة/التجزئة) لا على عمود واحد فقط.
• السعر الأساسي هو المرجع الجذري. عند غياب قاعدة نشطة لأي مستوى، يساوي سعر هذا المستوى السعر الأساسي تلقائياً. حذف قاعدة أو تعطيلها يعيد حساب المستويات المتأثرة ويعرض preview قبل الاعتماد عند وجود أثر كبير.
• قواعد متقدمة اختيارية: حد أدنى للهامش، عقود خاصة بعميل/مجموعة، تسعير حسب حجم السلة والوحدة والكمية، خصومات وBundles وBuy X Get Y وحسومات دورية/Rebates، وتواريخ سريان وانتهاء.
• Price Guard يمنع الخصم غير المصرح أو النزول دون الحد الأدنى للهامش. الاستثناء يحتاج صلاحية override وسبباً واعتماداً موثقاً.
• السعر الخاص بطلب واحد الذي يقره المستخدم المخول لا يغير قائمة السعر العامة. يجب أن يظهر الفرق في سجل الطلب وفي Audit Log.
• كل طلب يحتفظ بلقطة سعر (Price Snapshot) واسم/كود/وحدة الصنف والسعر والخصم والضريبة والإجمالي وقت الإرسال، ولا تتغير الفاتورة التاريخية عند تحديث قائمة الأسعار لاحقاً.

7. التسجيل والعملاء والحسابات
=============================

7.1 التسجيل والموافقة
---------------------
• التسجيل الأول يطلب الاسم، اسم المحل/الشركة، رقم الهاتف، وكلمة المرور، وأي معلومات يحددها المدير من إعدادات نموذج التسجيل.
• يدعم النظام 3 روابط دعوة مستقلة وثابتة يمكن إيقافها/تدويرها من لوحة التحكم، وتحدد فئة العميل المقصودة خادميًا عند فتح الرابط؛ لا تظهر الروابط الثلاثة علناً.
• بعد التسجيل تكون الحالة «بانتظار موافقة الإدارة» ولا يستطيع المستخدم إرسال طلب فعلي أو رؤية سعر/بيانات محمية قبل الاعتماد. صفحة الحالة تبين الخطوة التالية بوضوح.
• يستطيع المدير إنشاء عميل من تبويب العملاء وتحديد فئته ومعلوماته وحالة الموافقة وإرسال دعوة/تعليمات إكمال التسجيل.
• تسجيل الدخول برقم الهاتف وكلمة المرور مع إظهار/إخفاء كلمة المرور، وتذكر الجلسة اختيارياً بطريقة آمنة، وتسجيل الخروج من الأجهزة، واستعادة مستقبلية عبر OTP وفق مزود تحقق صالح.
• دعم اعتماد العميل أو رفضه أو تجميده أو حظره أو إعادة تفعيله أو أرشفته واسترجاعه، مع سبب وسجل تدقيق. تغيير فئة العميل يخضع لصلاحية محددة ويسجل قبل/بعد.
• يمكن إعداد سياسة جهاز واحد أو أكثر للجلسات من لوحة الأمان. عند إبطال جلسة سابقة يُعرض إشعار واضح للمستخدم.

7.2 ملف العميل وCustomer 360
----------------------------
يعرض للمستخدم المخول فقط ملفاً متكاملاً للعميل: جهات الاتصال والعناوين والمستخدمون التابعون، الطلبات، الإرجاعات، الإشعارات، الفواتير وكشوف الحساب القادمة من أونكس، الدفعات والذمم وحد الائتمان وتاريخ التفاعل والنزاعات والتنبيهات. لا تعرض مؤشرات المخاطر أو ملاحظات الإدارة للعميل نفسه.

8. الطلبات ودورة الاعتماد والفواتير
===================================

8.1 دورة الطلب القياسية
-----------------------
الحالات المقترحة: مسودة محلية للسلة، مرسل/جديد، تم الاستلام، قيد المراجعة، معاد للتعديل، معتمد، قيد التجهيز، تم التجهيز، خرج للتسليم، تم التسليم، ملغي، مرفوض، بانتظار التسوية/الدفع، ومحوّل إلى فاتورة بيع. تطبق الحالات المستخدمة حالياً وتُواءم دون كسر سجلاتها. كل انتقال حالة له صلاحية ووقت ومستخدم وسبب وسجل حالة.
• إنشاء الطلب والرأس والأسطر ولقطة الأسعار ولقطة الفاتورة وسجل الحالة والحجز المتوقع للأصناف يكون في Database Transaction ذرية واحدة أو سلسلة معاملات مصممة لضمان الاتساق. إما نجاح كامل أو لا تغيير.
• تعالج العملية مفتاح idempotency فريداً بحسب المؤسسة/العملية بحيث لا يؤدي النقر المتكرر أو إعادة إرسال الشبكة إلى تكرار الطلب/الفاتورة/رسالة الإشعار.
• يستطيع العميل استطلاع طلباته السابقة، إعادة الطلب، وإعادة إرسال طلب قابل للتعديل ضمن السياسة. عند إعادة طلب قديم، تُستخدم الأسعار الحالية ويُنشأ طلب جديد مرتبط بالأصل وليس نسخة مالية صامتة.
• يستطيع المدير تعديل الكميات المعتمدة والأسعار الخاصة بالطلب وحذف سطور مع توثيق السبب. بعد التعديل يرى العميل تنبيهاً مناسباً ولا يتغير السعر العام. الانتقال بين الأقسام مع إدخال تغيير غير معتمد يستلزم تنبيهاً وحفظاً/إلغاءً واضحاً.
• بعد تأكيد الإدارة يظهر للعميل الإجراء التالي المطلوب، مثل انتظار تأكيد التجهيز أو الدفع بحسب إعدادات النشاط. لا تتحول العملية إلى فاتورة بيع محاسبية نهائية إلا عبر قاعدة اعتماد صريحة وربط صحيح بأونكس.
• رقم الطلب يولد خادمياً بشكل غير مكرر، مع UUID داخلي ومعرّف أعمال مقروء مثل ORD-000001، وتخصيص unique constraint. معالجة التعارض في SQL/RPC عبر تأهيل جميع الأعمدة مثل orders.order_code.
• شريط متابعة الطلب يتحدث آلياً عند تغير حالته. عند إرجاعه للتعديل يظهر تنبيه بارز؛ وعند تعديل الأصناف/الكميات يظهر نص: «تنبيه: تم تعديل الأصناف/الكميات بحسب الكميات المتوفرة.» عند تحقق التعديل فقط.

8.2 ما يظهر للعميل مقابل الإدارة
--------------------------------

الموضع | السلوك الافتراضي المطلوب | التحكم الإداري
------ | ---------------------- | --------------
بطاقات وتفاصيل المنتجات | السعر المخصص لفئة العميل المعتمدة فقط. | يمكن تعطيل عرض السعر أو تغيير سياسة العرض.
السلة ومراجعة الطلب | إخفاء السعر والإجماليات في واجهة العميل وفق المطلب الأحدث؛ يظل وصف الأصناف والكميات ظاهراً. | إعداد مستقل لإظهار/إخفاء السعر والإجمالي في السلة والمعاينة.
طلباتي وتفاصيل الطلب/الفاتورة للعميل | إخفاء السعر والإجمالي وفئة العميل افتراضياً. | إعداد مستقل لكل شاشة ونوع مستند؛ لا يغير سجل الإدارة.
واجهة الإدارة والتصدير المحاسبي | القيم المالية الكاملة للمخولين فقط. | RBAC + سجل تدقيق + تأكيد عند التعديلات الحساسة.

مهم: إخفاء السعر في واجهة العميل لا يعني حذف السعر من قاعدة البيانات أو مستند التصدير المحاسبي؛ تبقى الأسعار كاملة في النظام والملف الموجه لأونكس للمستخدمين المخولين. تخضع ملفات Excel وPDF لصلاحيات التصدير ولا تنشأ روابط عامة مكشوفة.

9. أونكس برو والبيانات المحاسبية المتكاملة
==========================================

قرار معماري نهائي — أونكس برو جزء من التطبيق نفسه ومن بياناته وتقاريره؛ لا تُنشأ له بيئة تحليلية معزولة عن متجر الأغبري. المطلوب توحيد الرؤية والحركة مع الاحتفاظ بمصدر كل سجل ومفاتيحه ومطابقته حتى لا تختلط القيود أو تتضاعف الأرصدة.

9.1 تكامل تزايدي حسب الإمكانية الفعلية
--------------------------------------
• ابدأ بكشف آلية الربط الموجودة حالياً (API/قاعدة وصول مصرح بها/ملفات Excel/CSV). لا تخمّن API غير موثق ولا يتصل النظام بقاعدة أونكس مباشرة دون وثائق وصلاحية ونسخة احتياطية.
• إذا توفرت واجهة رسمية مستقرة، يُبنى Adapter/Connector خادمي يدعم الاستعلام والمزامنة والاستيراد/التصدير، المصادقة، تدوير المفاتيح، retry، idempotency، health check، ومراقبة الإصدارات.
• إذا لم تتوفر API، يستخدم مسار ملفي موحد من أونكس مع قوالب محفوظة وقواعد تحويل، ومعاينة، والتحقق، والمطابقة، والتصدير المتوافق؛ يبقى هذا المسار ضمن التطبيق وليس برنامجاً منفصلاً.
• تظهر ضمن لوحة التحكم والمالية والعملاء والطلبات والمخزون والتقارير بيانات أونكس المتصلة، مع مصدر كل سجل ووقت مزامنته وحالة المطابقة. يختار المستخدم الفترة والفرع والعميل والمخزن ثم تظهر لوحة موحدة واحدة.
• تعرض شاشة مزامنة أونكس: مصدر البيانات، آخر مزامنة، عدد السجلات الجديدة والمعدلة والمتجاهلة والمرفوضة، أخطاء المطابقة، الفرق قبل/بعد، زر «مزامنة الآن»، زر «مطابقة الآن»، سجل الدفعات والتراجع الممكن.
• لا تستبدل قيم Live DB عشوائياً بملف وارد؛ تستخدم قواعد فض تعارض قابلة للضبط: القيمة القائمة تفوز، الواردة تفوز، قبول تلقائي ضمن قاعدة، مراجعة بشرية، أو رفض السطر. لا يجري ترحيل القيود المالية تلقائياً من AI.
• يوضع مصدر الحقيقة لكل كيان في سجل Field Ownership/Mapping: ما يديره المتجر، ما يأتي من أونكس، ما يُسمح بالكتابة العكسية إليه، وما هو للقراءة فقط. الافتراضي عدم الكتابة العكسية إلى أونكس قبل اختبار الربط واعتماد المالك.
• تُدمج بيانات المبيعات والمخزون والذمم والموردين والبنوك/الصرافين والعملاء والأصناف التي توجد لها بيانات موثوقة من أونكس داخل مؤشرات التطبيق وفق صلاحياتها.

9.2 وظائف محاسبية ترفع قيمة المنتج
----------------------------------
• كشف حساب العميل، أعمار الذمم، الدفعات، الفواتير المفتوحة، حد الائتمان، الرصيد المتاح، التسويات ومطابقة الدفعات مع الفواتير.
• مركز التزامات الموردين، مواعيد الاستحقاق، تنبيهات السيولة النقدية، حركة البنوك/الصرافين إذا توفر مصدر صالح، ومؤشرات الفجوة النقدية.
• مطابقة أرصدة المخزون من أونكس مع المخزون التشغيلي؛ إظهار الفروق الكمية والقيمية وعدم تسوية أي فرق دون اعتماد وصلاحية واضحة.
• محاكاة تأثير تغيير السعر أو MOQ أو حد الائتمان أو خصم تعاقدي قبل اعتماده (What-if Simulator)، مع تسجيل السيناريو لا تغيير البيانات الحية إلا بأمر اعتماد.
• قفل وتسجيل الإغلاق اليومي/الفترة المحاسبية عند دعم النظام الأساسي لذلك، وتحديد من يقدر على إعادة فتحها.

9.3 شاشة التحليل الموحّد
------------------------
زر «ابدأ التحليل» يفتح صفحة تنفيذية واحدة ممتدة عمودياً تعرض KPIs، المخططات، الجداول التفصيلية، الانحرافات، التوصيات والتنبؤات من حركة متجر الأغبري وبيانات أونكس المدمجة معاً، وفق الفترة والفلاتر. ويظهر التنبيه: «تعتمد هذه الشاشة على البيانات التشغيلية المباشرة وبيانات أونكس برو المتزامنة، مع بيان مصدر كل مجموعة ووقت آخر تحديث».

10. الاستيراد والتصدير وجودة البيانات
=====================================

10.1 محرك استيراد موحد واحد
---------------------------
يجب استخدام مسار استيراد موحد حصري لكل Excel/CSV/PDF/مصادر أخرى. لا يُسمح لشاشة أو محرك جانبي بكتابة بيانات تتجاوز التحقق والمراجعة والتدقيق.
المسار: Upload → Staging → Detection → Column Mapping → Validation → Normalization → Deduplication → Chunking → Merge/Conflict Resolution → Snapshot → Commit → Analytics/AI. تعرض الشاشة تقدم المهمة وإمكانية الإلغاء والاستئناف وإعادة المحاولة للشرائح الفاشلة.

10.2 شروط السلامة
-----------------
• معاينة قبل الالتزام، Dry Run، عرض الفروقات Diff Preview، تحقق من المكرر، معرّف دفعة، سجل صفوف مقبولة ومرفوضة وأسبابها، وRollback لدفعة الاستيراد عندما يكون آمناً.
• احتساب بصمة SHA-256 لاكتشاف إعادة رفع الملف نفسه، مع خيارات تجاهل/استبدال/دمج/نسخة جديدة. الاستيراد القابل للاستئناف يدعم Upload Session والشرائح المتحققة.
• درجة جودة بيانات DQS من 0 إلى 100 على أساس الاكتمال والصحة والفرادة والاتساق والسلامة الزمنية/المرجعية: 90-100 ممتاز؛ 75-89 مقبول مع تحذيرات؛ 50-74 مراجعة بشرية؛ أقل من 50 رفض افتراضي للدفعة.
• حفظ أكواد الأصناف والعملاء والموردين كنص مع الأصفار البادئة؛ لا تحول SKU مثل 000125 إلى 125، ولا تستخدم floating point لحساب العملة.
• لا يخمن الذكاء الاصطناعي بيانات من PDF غير جدولي. إذا تعذر استخراج جدول موثوق، تعاد حالة Extraction Failed: Non-Tabular Format مع Manual Mapping Required.
• حدود ابتدائية قابلة للضبط: ملف حتى 100MB، حتى 100,000 صف، 100 عمود، 4,000 حرف للخلية، مع معالجة مجزأة وقيود وقت/ذاكرة وفك ضغط.
• عدم الاحتفاظ الدائم بملفات المصدر الخام إلا إذا كانت هناك حاجة تشغيلية وسياسة احتفاظ موافق عليها. يحتفظ النظام ببصمة الملف وmetadata والنتيجة المنظمة وسجل الاعتماد؛ تحذف الخام بعد TTL المحدد مع توثيق.
• يحوي كل ملف تعريف Import Profile الاسم والمصدر والنوع والإصدار والأعمدة المطلوبة والاختيارية والمتجاهلة والمرادفات وقواعد التغيير والتحقق ومفتاح المطابقة واستراتيجية الدمج وتاريخ الفترة.
• التغييرات في ملف التعريف لا تغيّر تفسير الدفعات التاريخية التي نفذت بإصدار أقدم؛ كل دفعة تحفظ رقم إصدار profile وnormalization.

10.3 التصدير
------------
تصدير Excel/PDF عربي رسمي بجداول قابلة للقراءة والفرز والطباعة، واسم ملف واضح، ووقت التصدير، ومعرف الطلب/التقرير، مع حماية حقن صيغ Excel للخلايا التي تبدأ بعلامات formula. يجب توفير قوالب منفصلة لتصدير العميل والطباعة وتكامل Onyx Pro؛ لا يفترض أن ملفاً بشري القراءة مطابق تلقائياً لتخطيط Onyx.

11. منصة الذكاء الاصطناعي المجانية والقابلة للتبديل
===================================================

11.1 بوابة موحدة متعددة المزودين
--------------------------------
• إنشاء AI Gateway/Provider Registry موحد بواجهات Adapter، بدلاً من ربط الشاشات بمزود واحد أو مفاتيح داخل الواجهة الأمامية. يضم المزود، النموذج، نوع المهمة، وضع مجاني/محلي/مدفوع، الحالة الصحية، حدود الطلب/اليوم/الشهر، وسياسة البيانات.
• يدعم كل مزود مجاني متاح وقابل للتكامل تقنياً وقت التنفيذ وفق API وشروطه، مع قابلية إضافة مزود جديد دون تعديل كل صفحات التطبيق. تشمل الخيارات نماذج مفتوحة المصدر محلية عند توافر موارد الخادم ومزودي API ذوي حصص مجانية عند صلاحية خططهم.
• أمثلة استرشادية لا ضمان دائم: Gemini API بخطة مجانية لبعض النماذج، ونماذج مجانية عبر بوابات مثل OpenRouter، واستضافة محلية لنماذج مفتوحة المصدر باستخدام أدوات مثل Ollama. يجب إعادة فحص الأسعار وحدود الحصص وسياسة البيانات وقت تفعيل كل مزود؛ المزايا المجانية قابلة للتغيير وليست وعداً بسعة غير محدودة.
• جميع المفاتيح تحفظ في مخزن أسرار خادمي/مشفّر مع إظهار حالة الاتصال وتاريخ الفحص وآخر خطأ؛ لا تظهر القيمة السرية كاملة بعد الحفظ ولا ترسل للمتصفح أو ملفات السجل.
• إعداد نموذج أساسي، ونموذج احتياطي، وأولوية توجيه لكل مهمة، ووزن/حد تكلفة، وحد زمني، وسياسة Retry/Circuit Breaker، والتحول إلى مزود آخر أو تحليل قاعدي عند انتهاء الحصة أو الفشل.
• إمكانية تعطيل مزود أو نموذج من لوحة التحكم، إجراء Test Connection، معرفة آخر استخدام والحصة والتكلفة التقديرية، وتحديد سقف يومي/شهري وسقف لكل طلب. عند وصول الحد تتوقف الطلبات التوليدية وتعمل التقارير القاعدية بدلاً منها.
• استخدام تقنيات مجانية/مفتوحة المصدر للحسابات والتحليل والتنبؤ الأساسي حيث تناسب، حتى لا يصبح استمرار التقارير معتمداً على API خارجي.
مراجع مراجعة الخطط والحصص وقت التنفيذ (استرشادية وليست ضماناً ببقاء أي خطة مجانية):
Gemini API pricing: ai.google.dev/gemini-api/docs/pricing
OpenRouter free models/pricing: openrouter.ai/pricing
Ollama local models: ollama.com

11.2 حدود الذكاء الاصطناعي والخصوصية
------------------------------------
• الأرقام المالية والحسابات الدقيقة (الإجمالي، الربح، الهامش، أعمار الديون، دوران المخزون) تحسب في SQL/Domain Engine حتمي ومختبر؛ لا يُسمح للنموذج اللغوي باختراع نتائج رقمية.
• يقرأ النموذج المقاييس المحسوبة والاتجاهات ويصوغ التفسير والتوقعات والتوصيات، مع مصدر البيانات والفترة وحجم العينة والافتراضات ودرجة الثقة والأثر المتوقع.
• قبل تمرير أي بيانات لنموذج خارجي: تنقية/تقليل البيانات، إخفاء الأسماء وأرقام الهاتف والهوية والمعلومات الحساسة، كشف Prompt Injection، وبناء سياق منظم موثوق. البيانات الحساسة تبقى محلياً/خاصاً ما أمكن، ولا ترسل بيانات خام خارجياً دون إعداد موافقة صريح.
• كل رد AI يسجل model/provider/version/prompt version/request id/مدة التنفيذ/استهلاك/نتيجة السلامة ومصدر snapshot. لا تسجل مفاتيح API أو كلمات مرور أو محتوى حساس غير لازم.
• إذا لم تتوفر بيانات تاريخية كافية لا يصدر تنبؤ تخميني؛ تظهر رسالة واضحة «لا تتوفر بيانات تاريخية كافية لتنبؤ موثوق» ويذكر النظام ما يلزم لتحسينه.
• يمنع منح النموذج صلاحية تنفيذ معاملات مباشرة. يتحول اقتراحه إلى Action Card تعرض الإجراء والأثر ثم تتطلب صلاحية واعتماداً بشرياً للأفعال المالية أو التي تغير المخزون والأسعار والائتمان.

11.3 دفتر استهلاك الذكاء
------------------------
سجل مستقل للاستهلاك يحتوي على الأقل: request_id، model/provider، tokens/input-output إن توفرت، تقدير التكلفة، زمن التنفيذ، تاريخ الطلب، المهمة، حالة الطلب، وحد المؤسسة/المستخدم. تعرض الإدارة استخدام اليوم والشهر وأسباب التحول إلى fallback؛ تُراعى حدود التزويد المجاني دون الاعتماد على أنها ثابتة.

12. التقارير التنفيذية والتنبؤية والاستشارية
============================================
كل التقارير تكون عربية، قابلة للتصفية حسب الفترة والفرع والمخزن والمجموعة والصنف والعميل والمورد ومصدر البيانات، وقابلة للتصدير إلى Excel/PDF، وتوضح آخر تحديث ومصدر الأرقام. التقارير الذكية واللوحة التنفيذية والمساعد والتنبيهات تستهلك خط أحداث واحداً وطبقة مقاييس موحدة.

------ | ---------------------- | -----------
المبيعات والطلب | مبيعات يومية/أسبوعية/شهرية، نمو وانحراف عن الفترة المقارنة، عدد الطلبات ومتوسط السلة، المنتجات والفئات الأكثر والأقل حركة، المبيعات المفقودة عند نفاد المخزون. | الحساب عبر بيانات الطلبات المعتمدة فقط، مع تمييز الطلبات الملغاة وغير المكتملة.

------------------------------
كل توصية تعرض: العنوان، السبب Why، المقاييس المصدرية Source Metrics، الحساب/الطريقة Calculation، نطاق الفترة، Snapshot ID، درجة الثقة، حالة الثقة (موثّق/تقديري/معلّق/قديم)، الأثر المتوقع، المخاطر، الإجراء المقترح، وحالة التنفيذ. أمثلة إجراءات: «عرض حركة الصنف»، «إنشاء مسودة أمر شراء»، «محاكاة تغيير سعر»، «متابعة عميل»، «تجاهل». الإجراءات التي تُنشئ أثراً حقيقياً تتطلب معاينة وصلاحية واعتماداً.

12.2 التحليل التنفيذي والبيانات الموحدة
---------------------------------------
تعرض صفحة التحليل التنفيذي بيانات التطبيق المباشرة وحركة أونكس المدمجة. يجب التفريق بين actual وforecast وبين data source وsnapshot time. لا يتكرر احتساب نفس المستند القادم من أونكس والمستورد سابقاً في مبيعات المتجر؛ تستخدم مفاتيح مطابقة ومعرفات مستند أصلية ومعالجة تكرار حتمية.

استثناءات أمنية: لا تُخزن أسرار البنية الرئيسية أو مفاتيح التشفير أو بيانات اتصال قاعدة البيانات بصيغة مكشوفة داخل جدول إعدادات عام؛ تُدار في مخزن أسرار خادمي. يمكن للمدير المخول إدخال/تدوير المفتاح ورؤية حالته وآخر أربعة أحرف فقط، لا استعادة قيمته النصية.

14. الإشعارات وWhatsApp والتكاملات
==================================

14.1 الإشعارات
--------------
• مركز إشعارات داخل التطبيق مع سجل للمستخدم والرسالة والوجهة والوقت والحالة وسبب الفشل، وإشعارات realtime أو polling احتياطي عند انقطاع WebSocket.
• Push على الأجهزة يتطلب Service Worker ومفاتيح وقناة Push حقيقية مفعلة (مثل FCM أو Web Push حسب المنصة). لا تسمى الإشعارات الداخلية Push.
• رسائل تسجيل العميل، الموافقة/الرفض، الطلب الجديد، تعديل الطلب، التجهيز، التسليم، عروض اليوم، انخفاض المخزون، ومهام المزامنة الفاشلة بحسب صلاحية المستخدم وتفضيلاته.
• WhatsApp: إعداد رقم الإدارة والعميل ورسائل القوالب من لوحة التحكم حيث تسمح المنصة. تسجيل حالة Submitted/Queued/Sent/Delivered/Failed، والمرجع الخارجي. لا اعتبار الرسالة مرسلة لمجرد إنشاء رابط أو ملف.
• للإرسال التلقائي مع ملف Excel، يستخدم خادم التطبيق API رسمي مع وسيط خلفي يخفي مفاتيح الاتصال. إذا لم يتوفر API أو لم يتم توثيقه، يبقى تنزيل Excel ورسالة بديلة أوتوماتيكية الحالة موضحاً أنه بديل يحتاج تفاعلاً من المستخدم.
تدفق إرسال الطلب: بعد الحفظ الذري، يمكن تنزيل نسخة Excel/ملخص طلب إلى جهاز العميل تلقائياً بحسب إعداد المتصفح، وتكون نسخة العميل بلا أسعار افتراضياً وفق سياسة الخصوصية. يرسل الخادم ملخص الطلب النصي إلى رقم الإدارة عبر قناة WhatsApp Business رسمية مفعلة؛ لا يلزم فتح WhatsApp لدى العميل إذا كان الإرسال الخادمي مفعلاً. يصل إشعار داخل لوحة الإدارة يفتح تفاصيل الطلب في صفحة مستقلة وبداخلها زر لتنزيل قالب Excel الكامل المتوافق مع أونكس برو. إرفاق ملف Excel نفسه في WhatsApp يكون إعداداً مستقلاً ولا يفعل إلا إذا كان API الرسمي المعتمد يدعمه. عند غياب API، تُعرض حالة «لم يُرسل - القناة غير مهيأة» بوضوح مع بديل يدوي، ولا يُزعم الإرسال.

14.2 مركز تكاملات عام
---------------------
طبقة Integration Hub تشمل Onyx، WhatsApp، البريد أو مزود الرسائل، API، Webhooks. لكل اتصال اسم وحالة صحية وآخر نجاح/فشل ومعدل retries وصلاحية المفتاح وسجل عمليات، مع تدوير الأسرار وتحديد rate limit ونطاقات مفاتيح API وسجل توصيل Webhooks. أي تكامل غير مهيأ يبقى «غير مفعّل» بوضوح ولا يولد نجاحاً كاذباً.

15. الأمن والخصوصية والحوكمة
============================

15.1 ضوابط إلزامية
------------------
• RLS على جميع الجداول الحساسة واختبارات سلبية تثبت أن العميل A لا يقرأ أو يعدّل بيانات العميل B ولا يمكنه تمرير user_id أو organization_id لتجاوز سياق جلسته.
• استنتاج المستخدم والمؤسسة والفئة والصلاحيات خادمياً من الجلسة/claims الموثقة؛ لا يثق السيرفر بالقيم الحساسة القادمة من المتصفح.
• كلمات المرور hashed باستخدام خوارزمية مناسبة تديرها منصة المصادقة، مع فحص قوة، تدوير جلسات، حد محاولات الدخول، rate limiting، حماية brute force، MFA للمالك/الإدارة حيث يدعمه النظام.
• عدم تخزين كلمات المرور أو token أو service role keys في localStorage أو logs أو مصدر الكود أو exports. لا تعرض أي سر في الواجهة ولا تنفذ bootstrap-admin مفتوحاً بعد التهيئة.
• إبطال الجلسات المنتهية، إدارة الأجهزة والتغييرات المصرح بها، سجل دخول يتضمن تاريخاً وجهازاً ومعلومات شبكة حسب ما هو متاح وقانوني، مع تقليل الاحتفاظ بالبيانات الحساسة.
• حماية SQL Injection عبر الاستعلامات المعلّمة/الطبقة الآمنة، XSS عبر escaping/sanitization، CSRF حيث توجد جلسات cookies، CORS وسياسات CSP وHTTPS وحدود حجم الطلبات.
• تحديد Rate Limits لخدمات المصادقة والبحث والاستيراد والتصدير والـ APIs والذكاء الاصطناعي مع كشف إساءة الاستخدام.
• سجل Audit غير قابل للتعديل من واجهة المستخدم العادية يسجل الفاعل والكيان والفعل والقيم السابقة/الجديدة والسبب والوقت وrequest ID والنتيجة.
• حذف منطقي Soft Delete للكيانات المناسبة مع استعادة مسجلة؛ يمنع الحذف النهائي للسجلات المالية/التدقيقية إلا بسياسة احتفاظ وصلاحية موثقة.
• تشفير النقل HTTPS وتشفير الأسرار والمعلومات الحساسة عند السكون وفق قدرة البنية، وفصل صلاحيات التشغيل وقاعدة البيانات والتصدير.
• التعامل مع ملفات المستخدم كمدخل غير موثوق: فحص MIME والحجم والامتداد، حماية zip bombs، منع تنفيذ macros، حماية الصيغ في Excel، وفحص Prompt Injection قبل إرسال محتوى للذكاء الاصطناعي.
• لا يُفرض منع تكرار كلمات المرور عبر حسابات المستخدمين؛ يستخدم بدلاً عنه كشف كلمات المرور الضعيفة/المسرّبة إن توافرت خدمة موثوقة، وMFA ومسارات استرداد آمنة.

15.2 خصوصية الأسعار والملفات
----------------------------
يختبر النظام تسرب الأسعار على كل طبقة: واجهة العميل، API، RPC، View، استجابة JSON، Cache، سجل الخطأ، تصدير الملفات وملفات الطلبات. يجب أن تحتوي Cache Keys على سياق المستخدم/الفئة/الكيان/الإصدار المناسب، وألا يعاد استخدام كاش مستخدم لفئة أخرى. جميع ملفات Excel وPDF الخاصة تطلب رابط تنزيل محمياً قصير العمر أو تتحقق من صلاحية المستخدم عند التنزيل.

16. الأداء وPWA والعمل مع الإنترنت الضعيف
=========================================
• Lazy loading للمسارات والمكونات، Pagination أو infinite scrolling للبيانات الكبيرة، Virtualized tables حيث يلزم، وعدم جلب كل الكتالوج دفعة واحدة.
• استخدام TanStack Query/SWR أو النظام الموجود لجلب البيانات مع stale/cache/refetch policies موحدة وإبطال الكاش عند تغير السعر/المخزون/الحالة.
• ضغط صور وتحويلها إلى WebP/AVIF وصور مصغرة وresponsive sizes وlazy loading وCDN عند توفره ضمن التكلفة المقبولة. لا تجعل إضافة CDN شرطاً يوقف الإطلاق إن وفرت المنصة الحالية CDN مناسباً.
• PWA فعلي: manifest، أيقونات، Service Worker، install prompt حيث يدعمه المتصفح، تحديث نسخة التطبيق، cache محدود للملفات والكتالوج المسموح به، وصف واضح لحداثة البيانات.
• عند انقطاع الشبكة يمكن عرض آخر بيانات متاحة مذكور عليها وقت التحديث. لا يُعتمد الطلب/المخزون/الدفعة Offline. السلة المحلية يمكن حفظها ثم التحقق من السعر والمخزون خادمياً عند إعادة الاتصال.
• هدف الأداء: واجهات المتجر الأساسية خلال نحو ثانيتين في المئين 75 على جهاز واتصال مرجعي محدد، وAPI التفاعلي P95 < 300ms في عمليات القراءة الخفيفة الممكنة بعد قياس baseline. لا يعلن هذا الرقم قبل قياسه، والمهام الثقيلة تعمل بالخلفية.
• عالج Cache Stampede بطلب مشترك/SingleFlight وTTL Jitter وNegative Caching عند الحاجة، ومفاتيح الكاش تشمل tenant/entity/version/snapshot عند انطباقها.
• عند انقطاع WebSocket يتحول النظام إلى polling مضبوط من دون فقد حالات أو تكرار آثار جانبية.
• تحديث التطبيق: زر تحديث/إعادة تحميل البيانات داخل الواجهة، وإشعار بإصدار جديد للـ PWA مع تحديث Service Worker بطريقة لا تكسر جلسة المستخدم أو بياناته.

17. قاعدة البيانات وواجهات API والأحداث
=======================================

17.1 نموذج بيانات منطقي
-----------------------
تُراجع الجداول الحالية ويعاد استخدام الموجود. يجب أن تغطي البنية الكيانات المنطقية التالية على الأقل دون إنشاء جداول مكررة لمجرد تغيير الأسماء: users/profiles، roles/permissions، customer_categories، invitations، companies/addresses/contacts، products/categories/brands/units، product_prices/pricing_rules/price_change_log، inventory/warehouses/stock_movements/reservations، orders/order_items/order_status_history، invoices/payments/receivables/supplier_obligations إذا كان مصدرها متاحاً، notifications، audit_logs/login_history/user_devices، import_jobs/import_job_rows/import_profiles/import_snapshots، integration_connections/onyx_sync_log/reconciliation, ai_snapshots/ai_alerts/ai_tasks/ai_recommendations/ai_usage_ledger، outbox_events/outbox_consumptions، system_restore_points/release_notes.

17.2 معايير قاعدة البيانات
--------------------------
• UUID للمفاتيح الداخلية حيث يتوافق مع المخطط، مع معرف عمل مقروء للطلب/المستند عند الحاجة. UNIQUE constraints للمفاتيح التجارية ومفاتيح idempotency.
• فهارس للبحث والتصفية والترتيب والربط على الحقول الحرجة: item_code/SKU/barcode/category/status/customer_id/created_at/updated_at/order_code/source_document_id حسب أنماط الاستعلام الفعلية.
• عمليات مالية/مخزون عبر transactions وتقييد optimistic/pessimistic concurrency الملائم، ودقة Decimal للمال بدلاً من float.
• Full-text search أو بحث fuzzy بالاسم والوصف والكود والباركود مع إعادة فهرسة في الخلفية بإصدار normalization واضح ودون توقف الخدمة.
• تاريخ تغيّر حالة الطلب وتعديلات الأسعار والمخزون لا يعتمد على قيمة status الحالية وحدها؛ كل حدث تاريخي محفوظ.
• جميع المهاجرات مؤرخة ومراجعة ومعها استعلامات تحقق قبل/بعد وخطة Rollback أو Roll-forward مناسبة.

17.3 REST API وتوثيقه
---------------------
إذا كان للمشروع REST API عام أو داخلي، توحد صيغة JSON وأكواد HTTP: 200/201/204 للنجاح، 400 للمدخلات غير الصحيحة، 401/403 للمصادقة والصلاحية، 404 للمفقود، 409 للتعارض/تكرار الطلب، 422 لفشل التحقق، 429 لتجاوز الحد، و5xx لأخطاء الخادم دون كشف التفاصيل الحساسة. توثق الواجهات في OpenAPI/Swagger ببيئات واضحة وأمثلة غير حساسة؛ وتوثق RPC/Edge Functions/التكاملات بنفس المستوى حتى إن لم تكن REST خالصة.

17.4 الطوابير والمهام الخلفية
-----------------------------
تخصص مسارات معالجة للاستيراد والتحليلات والتنبؤ والذكاء والتصدير/الإشعارات مع قيود للذاكرة والوقت وعدد المحاولات. الرسالة الميتة DLQ تعرّض سبب الفشل وإجراء retry/replay. تكتب العملية والحدث داخل معاملة واحدة عبر Transactional Outbox ثم تستهلكها خدمات محصنة من التكرار لتحقيق Effectively-once business processing.

18. المراقبة والنسخ الاحتياطي والتعافي
======================================
• سجل أخطاء منظم في الواجهة والخادم، Error Boundaries، request/correlation ID، وأداة مراقبة قابلة للاستبدال مثل Sentry أو البديل المتاح. يمنع تسجيل الأسرار أو البيانات الحساسة الخام.
• صفحة صحة النظام تعرض حالة قاعدة البيانات والتخزين والمزودين والمهام والطوابير والمزامنة وأحدث خطأ مع إجراءات Retry آمنة.
• نسخ احتياطي آلي وفق قدرات قاعدة البيانات ومزود الاستضافة، وتحديد Retention، وتشفير النسخ وصلاحياتها؛ والأهم إجراء اختبار استعادة دوري موثق بدلاً من الاكتفاء بوجود النسخ.
• خطة تعافي Disaster Recovery تحدد RPO/RTO بالاتفاق مع المالك وقياس القدرة الفعلية، وخطوات الاستعادة ومالك كل خطوة وآخر تمرين ناجح.
• نقاط استعادة قبل التحديثات الكبيرة، سجل إصدار وملاحظات التغيير، وإمكانية الرجوع الآمن عند فشل الترحيل أو البناء.
• مراقبة الأداء والاستعلامات البطيئة واستخدام الموارد وعمق الطوابير ومعدل الأخطاء وسعة التخزين وحصص AI وWhatsApp وOnyx.

19. الاختبارات ومصفوفة القبول
=============================
يجب أن تشمل الاختبارات Unit وIntegration وRLS/Security وE2E وRegression وUAT. تستخدم أدوات الاختبار المتوافقة مع بنية المشروع الحالية ولا يفرض تبديل الـ stack. تنفذ سيناريوهات الاختبار ببيانات اختبار واضحة ولا يتم العبث ببيانات إنتاج حقيقية.

19.1 حالات قبول إلزامية
-----------------------

المعرف | سيناريو الاختبار | معيار القبول والدليل
------ | ---------------- | --------------------
ID-01 | تدقيق هوية المشروع | لا تظهر أسماء العامري/Alamri/Amiri كهوية للمنتج في الصفحات وmetadata وPWA والتقارير بعد البحث الشامل.
SEC-01 | عميل من الفئة الأولى يحاول استخراج سعر الفئتين الأخريين بتغيير API/RPC أو Cache | رفض أو إخفاء خادمي؛ لا توجد قيمة سعر أجنبي في الاستجابة. يقدم اختبار سلبي وسياسة RLS/لقطة network.
REG-01 | فتح رابط دعوة الفئة ثم التسجيل | يسجل العميل بالفئة الصحيحة خادمياً وحالة Pending؛ لا يستطيع إرسال الطلب حتى الموافقة.
IMP-01 | استيراد 1,000 صنف تتضمن item_code=000125 | يبقى الكود نصاً بالأصفار البادئة؛ إعادة الملف لا تكرر السجلات؛ يقدم Manifest وقيم DB.
IMP-02 | رفع ملف متكرر أو ملف DQS أقل من 50 | يكشف التكرار أو يرفض حسب السياسة؛ لا تعدل البيانات الحية قبل اعتماد.
PRC-01 | إنشاء قاعدة تسعير لكل واحد من مستويات الجملة والتجزئة وجملة الجملة | تحسب القاعدة في المستوى المختار؛ عند إزالة القاعدة يرجع المستوى المتأثر إلى السعر الأساسي تلقائياً.
ORD-01 | النقر على إرسال الطلب عدة مرات أو إعادة إرسال الشبكة | ينشأ طلب واحد فقط، وتظهر حالة صحيحة؛ لا يتكرر المخزون أو الإشعار أو الفاتورة.
ORD-02 | مراجعة الطلب وتعديله في الإدارة | تسجل اللقطة والتغييرات؛ يظهر التنبيه للعميل عند وجود تعديل؛ يظل السعر العام دون تغيير.
ERP-01 | رفع ملف أونكس وتطبيق Mapping ثم مزامنته مرتين | يظهر أولاً كسجلات جديدة، ثم لا تتكرر المستندات عند المزامنة الثانية، وتظهر الفروقات ومصدر كل سجل.
ERP-02 | استعراض تقرير مبيعات/ذمم موحد من المتجر وأونكس | تظهر البيانات من المصدرين داخل التقرير الموحد دون double counting مع تمييز المصدر/وقت المزامنة.
AI-01 | إدخال Prompt Injection داخل وصف/ملف مستورد | تنقية المدخلات؛ لا ينفذ النموذج تعليمات داخل بيانات الأعمال ولا يصدر تغييراً مباشراً.
AI-02 | إيقاف المزود الأساسي أو استنفاد حصته المجانية | تحول تلقائي إلى مزود احتياطي أو Rule-Based Fallback، مع سجل للسبب ودون ادعاء AI ناجح.
AI-03 | طلب تنبؤ دون تاريخ كافٍ | يرجع النظام بوضوح لعدم كفاية البيانات ولا يولد أرقاماً وهمية.
SEC-02 | عميل يغير user_id/organization_id في API | رفض بـ 403/الاستجابة الآمنة؛ يتم تحديد السياق من الجلسة الخادمية.
PERF-01 | اختبار تحميل على الكتالوج والطلبات بحجم واقعي | صفحات مجزأة، لا تحمل كل البيانات دفعة واحدة، وتقرير قياس P75/P95 والعتاد والاتصال.
PWA-01 | انقطاع الإنترنت ثم العودة | يمكن تصفح آخر بيانات مخزنة مع تحذير freshness؛ لا يتم اعتماد طلب غير متصل؛ لا ينشأ طلب مكرر بعد العودة.
BK-01 | استعادة نسخة احتياطية في بيئة اختبار | نجاح استعادة موثق مع فحص عدد السجلات والقيود وعينة مستندات.
WA-01 | اختبار إرسال واتساب دون مزود رسمي ثم بعد تفعيله | قبل التفعيل لا يدعي الإرسال؛ بعد الربط يثبت external message ID والحالة، وتسجيل الفشل وإعادة المحاولة.
XLS-01 | تصدير طلب إلى قالب Onyx | تطابق الأعمدة والترتيب والقيم كالنصوص/التواريخ، ويفتح الملف دون فساد ويجتاز الاستيراد التجريبي في أونكس عند توفر بيئة الاختبار.

19.2 الأدلة المطلوبة مع كل دفعة عمل
-----------------------------------
• Commit SHA السابق والحالي، git diff مختصر، الملفات والمهاجرات المتأثرة، وأي قرار معماري.
• نتيجة lint/typecheck/build والاختبارات المرتبطة، وعدد الاختبارات الفاشلة/المتجاوزة مع سبب صريح.
• تقرير E2E أو فيديو/لقطات لمسارات القبول الحساسة، ولقطات أو استعلامات آمنة تثبت قاعدة البيانات وRLS.
• نتائج اختبار التراجع على المسارات التي يُحتمل تأثرها، وأداء قبل/بعد إذا مست التعديلات الأداء.
• جدول Requirement Registry يبيّن الحالة (PASS/PARTIAL/BLOCKED/NOT DONE) والدليل المرتبط بها؛ لا يستخدم PASS بلا دليل.

20. مراحل الإنجاز والتسليم النهائي
==================================
التنفيذ incremental؛ لا يُعاد المشروع من الصفر. يجهز المطور خريطة فنية مرة واحدة ويحدّثها بعد كل مرحلة. لا ينتقل من مرحلة حرجة قبل نجاح اختبارات القبول الخاصة بها.

المرحلة | نطاق الإنجاز | بوابة الخروج

0. التدقيق وخط الأساس | Architecture audit، استنساخ/بناء، شجرة الصفحات، خريطة الجداول والصلاحيات والتكاملات، تقرير فجوات. | تشغيل baseline وقائمة تغييرات تمنع الكسر.
1. البيانات والاستيراد | المحرك الموحد، profiles والمرادفات، DQS، التكرار، المعاينة، التراجع، سجلات الدفعات. | اختبارات أصفار الأكواد والتكرار والملفات الفاسدة.
2. قاعدة موحدة وأونكس | ربط/استيراد أونكس، نموذج البيانات الموحد، المطابقة، ownership وlineage، تقارير بيانات المصدرين. | مزامنة مكررة بلا ازدواج، ومؤشرات مع مصدر واضح.
3. التجارة والتسعير | قواعد الأسعار الثلاثة، الأمان خادمياً، السلة والطلب الذري، الموافقات والتعديلات والتصدير. | تجاوز السعر وفشل الشبكة والتزامن لا يسبب بيانات خاطئة.
4. الأحداث والأداء | Outbox/Queues، البحث والكاش، invalidation، مراقبة الأخطاء، وإشعارات صحيحة. | اختبارات retry/replay بلا آثار مزدوجة.
5. الذكاء والتقارير | AI Gateway ومزودون/بدائل، الحسابات الحتمية، Action Cards، التقارير والتنبؤات والحوكمة. | ثقة ومصدر بيانات واضحان، fallback عند فشل/حد المزود.
6. الأمن | RLS/RBAC، الأسرار والجلسات، Rate Limits، اختبارات الخصوصية والملفات. | اجتياز الاختبارات الأمنية السلبية دون تجاوز.
7. PWA والتعافي | تثبيت/Cache/Offline قراءة، سرعة، backup/restore، UAT. | قياسات أداء واختبار استعادة موثقان.
8. الإطلاق والإغلاق | Full E2E وRegression، ملاحظات إصدار، وثائق، تدريب، handover. | كل بند إما PASS بدليل أو BLOCKED بسبب خارجي محدد ومقبول صراحة.

20.1 Definition of Done
-----------------------
• واجهة فعلية مرتبطة بعملية الخادم وقاعدة البيانات، مع validation وloading/empty/error/retry/success/unauthorized/offline حسب السياق.
• صلاحيات مفروضة على الخادم وRLS، لا أزرار مخفية فقط.
• اختبارات الوحدة والتكامل وE2E/Regression ذات صلة ناجحة؛ migrations مطبقة وآمنة ومراجعة.
• لا placeholders ولا بيانات وهمية ولا نجاح زائف؛ لم يثبت تكامل خارجي إلا بمرجع عملي أو حالة توضح ما يمنع تفعيله.
• تحديث المستند الفني وشجرة المعمارية وسجل المتطلبات والأدلة وSHA، ثم مراجعة العميل/UAT.

20.2 التسليم وحقوق الملكية
--------------------------
• تسليم مستودع الكود المصدري كاملاً وتاريخ التغييرات والفرع المعتمد، وكل ملفات الواجهة والخلفية والـ migrations والـ RPC/Edge Functions والاختبارات.
• تسليم ملف .env.example خالٍ من الأسرار، وقائمة أسماء المتغيرات ومصدر كل سر وطريقة توليده وتدويره دون كشف كلمات المرور في المستند.
• دليل تثبيت وتشغيل ونشر وتراجع، ودليل مستخدم، ودليل مدير، ودليل إعداد التكامل مع Onyx وWhatsApp ومزودي AI.
• توثيق API/OpenAPI حيث ينطبق، مخطط قاعدة البيانات وعلاقاتها وسياسات RLS وصلاحيات RBAC والنسخ الاحتياطي والاستعادة.
• قائمة الخدمات والتكاليف المتوقعة المجانية/المدفوعة وحدود الحصص والاستضافة والنطاق والتخزين والرسائل، مع عدم تفعيل خدمة مدفوعة دون موافقة مكتوبة من المالك.
• نقل ملكية مستودع الكود والخدمات والنطاقات وبيئات النشر ومفاتيح المالك إلى حسابات يملكها العميل، لا حسابات شخصية للمطور وحده.
• ضمان إصلاح أخطاء بعد التسليم لمدة لا تقل عن 3 أشهر، ويفضل 6 أشهر بالعقد، مع توضيح ما يعد خطأ وما يعد تطويراً جديداً.
• تقرير نهائي صريح بكل المتطلبات PASS/PARTIAL/BLOCKED/NOT DONE؛ لا قبول نهائي لوظيفة حاسمة من دون دليل تشغيل واختبار.
