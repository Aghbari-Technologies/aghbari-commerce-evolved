## Operating mandate

تنفيذ برمجي مباشر على المشروع القائم. لا تحوّل التكليف إلى خطة أو تقرير تدقيق، ولا تعِد قراءة المواصفات من البداية، ولا تنتظر المستخدم، ولا تطلب منه تكرار هذا البروتوكول. لا تدّع إنجازًا أو حفظًا أو نجاح اختبار دون دليل من المستودع أو نتيجة تشغيل تخص النسخة المعنية.

## Startup and resumption

1. اقرأ `ops/AGHBARI-LATEST-EXECUTION-STATE.md` أولًا.
2. اقرأ أحدث حالة فعلية من GitHub: الفرع، HEAD، PR، ونتائج CI المرتبطة بالرأس نفسه. لا تعتمد على SHA في المحادثة أو هذا الملف دون إعادة تحقق.
3. إذا اختلف سجل الحالة مع الكود وسجل Git، فالكود المحفوظ وGit هما المرجع. صحّح الحالة بعد التحقق.
4. افتح فقط ملفات المهمة التالية والفحوص اللازمة لتجنب التعارض؛ لا تعِد الاستكشاف العام.
5. انتقل مباشرة إلى `next_task_id`. إذا اكتمل، حدّث الحالة وحدد المهمة المستقلة التالية ثم واصل.

## Execution and persistence loop

لكل دفعة مترابطة: عدّل الكود الفعلي؛ افحص التغيير لمنع إتلاف وظائف قائمة أو تسريب أسرار أو إدخال بيانات غير صحيحة؛ شغّل أصغر الاختبارات الملائمة؛ احفظ commit واضحًا على فرع العمل؛ ادفع إلى GitHub حين تسمح الصلاحيات؛ حدّث سجل الحالة؛ ثم تابع.

- لا تجعل نجاح بند أو البناء نهاية الجلسة إذا بقيت أعمال مستقلة ممكنة.
- لا تعتبر تعديلًا محليًا أو Blob غير مربوط بفرع حفظًا دائمًا. تحقق من وجود commit على الفرع البعيد.
- لا تدّع حفظ تغييرات جزئية لم تُضمّن في commit. عند قرب الانقطاع، أوقف بدء أعمال جديدة، واحفظ الممكن أولًا، ثم تابع إذا بقي وقت.
- استخدم commit/tree وشرط `expected_sha` عند تحديث refs لتجنب الكتابة فوق رأس أحدث. إذا رُفض التحديث، أعد قراءة الرأس وادمج بأمان بدل فرض تحديث غير متحقق.
- لا تنشئ سجلات استئناف متعارضة أو مكررة. هذا البروتوكول هو قواعد التشغيل؛ ملف الحالة هو مؤشر التقدم الوحيد.

## Evidence and test rules

- سجّل SHA الفعلي ونتيجة GitHub Actions ورابط التشغيل وعدد الاختبارات/بواباتها، لا مجرد عبارة PASS.
- افصل بين الكود المنفذ، والاختبارات المحلية/المعزولة، والتكامل الحي، واختبار المتصفح الموثق، والإنتاج. نجاح PostgreSQL المعزول لا يثبت ترحيل الإنتاج؛ ونجاح build لا يثبت رحلة مستخدم.
- أعد الاختبارات المتأثرة فقط بعد إصلاح عطل، ثم نفّذ مجموعة القبول الملائمة على رأس الكود النهائي. لا تنقل نجاحًا إلى SHA مختلف دون إثبات.
- لا تحوّل قيمة مفقودة إلى صفر، ولا تعرض ماليات عند غياب سياسة العرض أو فشل التحقق، ولا تستخدم عينات/بيانات وهمية لإظهار الاكتمال.
- حدّث `docs/canonical/AGHBARI-REQUIREMENT-REGISTRY.md` مع كل دفعة قبول مهمة، وميّز بوضوح `IMPLEMENTED`, `TESTED`, `INTEGRATED`, `BROWSER-PROVEN`, `PRODUCTION-PROVEN`.

## Scope, security and external blockers

استكمل النواقص في المتجر وواجهات الإدارة والمنتجات والتصنيفات والأسعار والمخزون والعملاء والصلاحيات والسلة والطلبات والموافقات والفواتير والماليات وOnyx والاستيراد والتصدير والذكاء الاصطناعي والتقارير والإشعارات وPWA وقاعدة البيانات وRLS والأداء والرصد والاستعادة والاختبارات. قائمة البنود أو سجل المتطلبات لا يحددان سقف العمل بدل المواصفة الكاملة.

- حافظ على البنية والوظائف العاملة؛ لا تنشئ مشروعًا أو قاعدة بيانات بديلة.
- لا تحفظ أسرارًا أو رموز وصول في Git.
- لا تطبق تغييرات مدمرة أو ترحيلات على الإنتاج، ولا تدمج في `main` أو تنشر إصدارًا دون الصلاحيات والموافقات المطلوبة.
- استخدم Lovable فقط للخطوات التي تتطلب اتصال بيئته/قاعدة بياناته/المتصفح، وقلّل طلباته؛ جهّز الكود والاختبارات قبل الإحالة.
- عند عائق خارجي، نفّذ كل ما يمكن إثباته داخل المستودع، ثم سجّل اسم الخدمة/الصلاحية المفقودة بدقة. لا تستبدل المورد المقصود بمشروع مشابه الاسم.

## Session continuity

حدّث سجل الحالة بعد كل دفعة مهمة وقبل أي انقطاع محتمل، متضمنًا: المستودع والفرع والرأس الفعلي؛ آخر مرحلة منفذة؛ الملفات والسلوك المتغير؛ ما ثبت نجاحه برابط الاختبار؛ ما لم يُختبر؛ العوائق الخارجية؛ والمهمة التالية المحددة والملفات المستهدفة وخطوة البدء. يجب أن يستطيع مبرمج آخر الاستئناف دون سؤال المستخدم.
