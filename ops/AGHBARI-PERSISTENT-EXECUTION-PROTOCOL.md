# AGHBARI COMMERCE — PERSISTENT EXECUTION PROTOCOL

**Repository:** `Aghbari-Technologies/aghbari-commerce-evolved`
**Work branch:** `fix/acceptance-hardening-cart-finance-20261015` unless the latest PR metadata directs otherwise.
**Authoritative resume pointer:** `ops/AGHBARI-LATEST-EXECUTION-STATE.md`
**Requirement registry:** `docs/canonical/AGHBARI-REQUIREMENT-REGISTRY.md`

## Operating mandate

تنفيذ برمجي مباشر على المشروع الحالي. لا تحوّل التكليف إلى خطة أو تدقيق متكرر، ولا تطلب من المالك إعادة إرسال البيانات المحفوظة. لا تدّع نجاح اختبار أو حفظ أو تكامل بلا دليل.

## Single cursor and resumption

1. تحقق من الفرع/PR والرأس الفعلي وCI المطابق مرة واحدة.
2. خذ **معرّف المهمة الوحيد** من أول مؤشر في `ops/AGHBARI-LATEST-EXECUTION-STATE.md`؛ لا تكتب أو تستنتج مؤشرًا منافسًا في هذا الملف أو بقية التعليمات.
3. طابق المهمة مع صفها في `docs/canonical/AGHBARI-REQUIREMENT-REGISTRY.md`، واقرأ الكود وشروط القبول الضرورية فقط. لا تستكشف المشروع بالكامل من جديد.
4. إذا فشل CI للرأس الحالي، يبقى إصلاح الفشل وإثباته المهمة النشطة؛ لا تتجاوز فشلًا ولا تنتقل مبكرًا إلى المهمة التالية.
5. إذا اكتملت المهمة، حدّث مؤشر الحالة والصف المقابل بالأدلة، ثم اختر المهمة المستقلة التالية من سجل المتطلبات وحدّث المؤشر قبل بدء الدفعة الجديدة.

## Execution and mandatory checkpoint

لكل دفعة: عدّل الكود/الاختبارات، شغّل الاختبارات الملائمة، افحص الإخفاقات وأصلحها، ثم احفظ commit واضحًا على فرع PR الحالي. حدّث الحالة والسجل بعد كل دفعة **وقبل أي رد أو توقف أو timeout أو حد سياق أو نهاية جلسة**. يجب أن يشمل التقرير المحفوظ: فرع العمل وPR وHEAD، المسارات المتغيرة، أوامر الاختبار ونتائجها، SHA المختبر ورابط CI، مؤشر المهمة الحالي والتالي، والعائق ودليله. عند عدم تشغيل اختبار اكتب NOT RUN، وعند تعذر الرفع اكتب UNPUSHED. لا تعتمد على ذاكرة المحادثة للاستئناف.

- لا تجعل نجاح مرحلة أو البناء نهاية العمل إذا بقيت مهام مستقلة.
- لا تعتبر Blob أو تعديل غير موجود في commit على الفرع البعيد حفظًا دائمًا.
- لا تمسح تغييرات قائمة أو تعِد كتابة تاريخ منشور ولا تستخدم force-push.
- لا تنقل PASS بين SHA مختلفة.
- لا تدفع إلى `main` ما دام PR الحالي مفتوحًا؛ ادمج فقط عبر إجراء PR مقصود وبعد القبول.
- لا تكتب أسرارًا في Git ولا تطبق مهاجرات الإنتاج قبل تحقق هوية المشروع والصلاحيات.
- استخدم Lovable بعد تجهيز الكود والاختبارات وللخطوات التي تتطلب بيئته فعلًا؛ Git push ليس إثبات مزامنة أو نشر.
